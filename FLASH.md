## 1. What FlashORM is

FlashORM is a **SQL-first, type-safe ORM and code generator**. You write plain
SQL; Flash generates type-safe client code from it for **Go, TypeScript,
JavaScript, Python, Kotlin, Java, and Rust**.

Two inputs drive everything:

- `.flash/schema/` — table definitions (DDL, `.sql` files).
- `.flash/queries/` — named queries, each tagged with `-- name:`.

`flash gen` reads both and emits type-safe functions and structs.

> ⚠️ **Never edit generated files.** They are overwritten on every `flash gen`.
> Edit the `.sql` sources, then re-run `flash gen`.

## 2. Where generated code lives

The output directory is configured in `flash.toml` under `[gen.*].out`.
**Do not assume it is always `flash_gen/`** — users can change it.

To find the actual output path:

1. Read `flash.toml` in the project root.
2. Find the enabled `[gen.*]` block (e.g. `[gen.go]`, `[gen.rust]`).
3. The `out` field gives the directory. If `out` is absent, default is `flash_gen`.

Example:

```toml
[gen.go]
enabled = true
out = "internal/db/flash_gen"   # ← the real output directory
```

```toml
[gen.rust]
enabled = true
out = "src/db"                  # ← generated .rs files go here
```

When `flash gen` runs it prints `Output: <dir>/` so you can confirm the path.

## 4. Everyday workflow

```bash
# 1. (already done) flash init --sqlite
# 2. Edit schema
edit .flash/schema/users.sql
# 3. Create and apply migration
flash migrate "describe change"
flash apply
# 4. Write queries
edit .flash/queries/users.sql
# 5. Generate code (check flash.toml for the output dir)
flash gen
# 6. (optional) visual editor
flash studio
```

Fast iteration on a fresh dev DB: `flash apply` creates tables directly from
schema without migrations. For tracked incremental changes always use
`flash migrate "<msg>"` + `flash apply`.

Re-run `flash gen` after every `.sql` file change.

```toml
# [gen.js]
# enabled = true
# out     = "flash_gen"
# driver  = "pg"

# [gen.python]
# enabled = true
# out     = "flash_gen"
# async   = true
# driver  = "asyncpg"

# [gen.rust]
# enabled = true
# out     = "src/flash_gen"
# driver  = "sqlx"
# macros  = false                   # true = sqlx compile-time checked macros

# [gen.kotlin]
# enabled = true
# out     = "src/main/kotlin/com/example/flashgen"
# package = "com.example.flashgen"
# driver  = "jdbc"

# [gen.java]
# enabled = true
# out     = "src/main/java/com/example/flashgen"
# package = "com.example.flashgen"
# driver  = "jdbc"
```

**Multi-database:** replace `[database]` with `[[databases]]` blocks, each with
its own `name`, `provider`, `url_env`, and `[databases.gen.*]`. Target one with
`--db <name>` or set `default = true`.

```toml
[[databases]]
name     = "main"
provider = "sqlite"
url_env  = "MAIN_DATABASE_URL"
default  = true

[[databases]]
name     = "analytics"
provider = "clickhouse"
url_env  = "ANALYTICS_URL"
```

## 8. Writing schema (`.flash/schema/`)

Plain DDL. Scaffolded schema for `sqlite`:

```sql
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

```

Workflow: edit DDL → `flash migrate "<msg>"` → `flash apply` → `flash gen`.

Flash auto-detects column/table renames and preserves data.

## 9. Writing queries

Each query starts with exactly:

```sql
-- name: <QueryName> <:cmd>
```

`<QueryName>` becomes the generated function name.
`<:cmd>` controls the return type:

| `:cmd` | Returns | Use for |
|---|---|---|
| `:one` | one row (error if absent) | single-row SELECT, INSERT … RETURNING |
| `:many` | slice of rows | multi-row SELECT |
| `:exec` | nothing | INSERT/UPDATE/DELETE without return |
| `:execresult` | rows-affected / last-insert-id | MySQL inserts |

**Parameters use `?` placeholders for `sqlite`.**
Postgres uses `$1, $2, …`; MySQL/SQLite/ClickHouse/Scylla use `?`.

Scaffolded queries:

```sql
-- name: GetUser :one
SELECT id, name, email, created_at, updated_at FROM users
WHERE id = ? LIMIT 1;

-- name: CreateUser :one
INSERT INTO users (name, email)
VALUES (?, ?)
RETURNING id, name, email, created_at, updated_at;
```

Rules:
- Prefer `RETURNING` (Postgres/SQLite) so inserts can be `:one`.
- MySQL has no `RETURNING` — use `:execresult` for inserts.
- Any `.sql` file under `.flash/queries/` works; filenames are free.

## 11. Annotations

Placed as `--` comment lines directly before or after `-- name:`.

### `-- @required: col1, col2` (or `*`)
Marks columns as non-nullable in generated types even when the schema allows
NULL. Mainly for ScyllaDB (all non-PK columns are nullable by default in CQL).
`-- @required: *` marks every column.

```sql
-- name: GetUser :one
-- @required: name, email
SELECT id, name, email FROM users WHERE id = ?;
```

### `-- @json <field> { ... }` or `-- @json import <file>.json as <field>`
Declares a typed structure for a JSON/JSONB column so the generator emits a
typed class/struct instead of a raw string. (See `12` for full examples.)

### `-- @cache { ... }`
Caches a read query in Redis. (See `13` for full examples.)

## 12. Typed JSON columns

FlashORM can generate typed structs/classes for JSONB columns instead of raw
strings. Supported types: `string`, `int`, `float`, `boolean`, `string[]`,
`int[]`, `float[]`, `boolean[]`, `any`.

### Inline definition

```sql
-- name: GetUser :one
-- @json settings {"theme": "string", "language": "string", "font_size": "int", "dark_mode": "boolean"}
-- @json metadata {"level": "int", "badges": "string[]", "xp": "int"}
SELECT id, name, email, settings, metadata FROM users WHERE id = ?;
```

### Import from a JSON file

```sql
-- name: GetUser :one
-- @json import user_settings.json as settings
SELECT id, name, email, settings FROM users WHERE id = ?;
```

```json
// db/json/user_settings.json
{"theme": "string", "language": "string", "font_size": "int", "notifications": "boolean"}
```

Enable the JSON path in `flash.toml`:

```toml
json_path = "db/json"
```

### What gets generated

All fields are nullable. Unspecified fields are accessible via `.raw` / `.get("key")`.

```go
// Go — typed, no manual JSON parsing:
user, _ := q.GetUser(42)
theme  := user.Settings.Theme              // *string
level  := user.Metadata.Level             // *int
extra  := user.Settings.Get("custom_key") // untyped fallback
```

```kotlin
// Kotlin
val user = queries.getUser(42)
val theme  = user?.settings?.theme           // String?
val level  = user?.metadata?.level           // Int?
val extra  = user?.settings?.get("custom")   // any unspecified field
```

```typescript
// TypeScript
const user = await queries.getUser(42)
const theme = user?.settings?.theme          // string | null
const extra = user?.settings?.get("custom")  // unknown
```

```python
# Python
user = await queries.get_user(42)
theme = user.settings.theme if user else None   # str | None
```

```rust
// Rust
let user = queries.get_user(42).await?;
let theme = user.settings.as_ref().and_then(|s| s.theme.as_ref());
```

## 13. Query caching (Redis)

Enable in `flash.toml`:

```toml
[cache]
enabled       = true
redis_url_env = "REDIS_URL"
default_ttl   = "5m"
prefix        = "flash"
```

Add `REDIS_URL` to `.env`:

```
REDIS_URL=redis://localhost:6379
# or with auth:
REDIS_URL=redis://:password@redis-host:6379/0
```

### Annotating a query

```sql
-- name: GetUser :one
-- @cache {"ttl": "60s", "name": "UserCache", "tags": ["users"], "dep": ["UpdateUser", "DeleteUser"]}
SELECT id, name, email FROM users WHERE id = ?;

-- name: ListPublishedPosts :many
-- @cache {"ttl": "15s", "name": "PublishedPostsCache", "tags": ["posts"], "dep": ["CreatePost", "PublishPost", "DeletePost"]}
SELECT id, title, created_at FROM posts WHERE status = 'published' ORDER BY created_at DESC LIMIT ?;
```

`@cache` fields:

| Field | Meaning | Default |
|---|---|---|
| `ttl` | Time-to-live: `30s`, `5m`, `1h`, `24h`, `7d` | `default_ttl` from config |
| `name` | Cache accessor name | `<QueryName>Cache` |
| `tags` | Labels for bulk purge | none |
| `dep` | Mutation query names that auto-invalidate this cache | none |

### Generated code — cache-first query wrapper

```go
// Go — cache-first: hits Redis, falls back to DB, stores result
user, err := q.GetUserCached(42)

// Auto-purge wrapper: runs UPDATE then purges UserCache:{id}
err = q.UpdateUserAndPurge(arg)
```

```typescript
// TypeScript
const user = await getUserCached(queries, 42);
await updateUserAndPurge(queries, name, email, bio, id);
```

```python
# Python
user = await get_user_cached(queries, 42)
await update_user_and_purge(queries, name, email, bio, id)
```

```rust
// Rust
let user = queries.get_user_cached(42).await?;
queries.update_user_and_purge(params).await?;
```

```kotlin
// Kotlin
val user = cachedQueries.getUserCached(42, User::class.java)
cachedQueries.updateUserAndPurge(name, email, bio, id)
```

### Manual cache control via named accessors

Each `@cache` annotation also generates a named accessor:

```go
// Go
flash_gen.UserCache.Get(42)         // read from cache
flash_gen.UserCache.Set(42, user)   // write manually
flash_gen.UserCache.Del(42)         // delete one entry
flash_gen.UserCache.Purge()         // purge all UserCache:* entries
```

### Typed tag purging — bulk invalidation

Flash generates typed constants from your tag strings so you cannot misspell them:

```go
// Go — TagUsers, TagPosts, etc. are generated from your @cache "tags"
flash_gen.Cache.PurgeTag(flash_gen.TagUsers)   // purges UserCache, UserProfileCache, etc.
flash_gen.Cache.PurgeTag(flash_gen.TagPosts)
```

```rust
// Rust
CacheTag::Users.purge();
CacheTag::Posts.purge();
```

```typescript
// TypeScript
await purgeTag(CacheTag.Users);
await purgeTag(CacheTag.Posts);
```

```python
# Python
purge_tag(CacheTag.USERS)
```

```kotlin
// Kotlin
CacheTag.USERS.purge()
```

```java
// Java
CacheTag.USERS.purge();
```

## 14. Code generation & drivers

`flash gen` auto-detects project type (`package.json` → JS, `pyproject.toml` →
Python, `Cargo.toml` → Rust, Gradle/Maven → Kotlin/Java, else Go) and writes to
enabled `[gen.*]` targets. Force a full rebuild with `flash gen -f`.

After generation Flash prints `Output: <dir>/` — use this to confirm the
actual `out` path.

Drivers for `sqlite`:

```
# FlashORM — SQLite Drivers
#   Go:     "database/sql" (mattn/go-sqlite3, modernc.org/sqlite)
#   JS:     "better-sqlite3" | "bun:sqlite"
#   Python: "sqlite3" (sync) | "aiosqlite" (async)
#   Kotlin: "jdbc" (default) | "exposed"
#   Java:   "jdbc" (default)
#   Rust:   "sqlx" (default)
# Add driver = "<name>" inside the [gen.*] block below.
```

Set with `driver = "<name>"` inside the `[gen.*]` block.

### Generator selected by `flash init`

This project was initialized for **Rust**. The enabled block in
`flash.toml` is the source of truth; do not use examples for another language
unless you explicitly enable that additional `[gen.*]` target.

```toml
# Cargo.toml
sqlx = { version = "0.9", features = ["runtime-tokio", "postgres", "macros"] }
```

Generated files are Rust modules under `[gen.rust].out`. Include the module
with `mod flash_gen;`, create a `sqlx::PgPool`, then call async methods on
`flash_gen::db::Queries`; results are `Result<T, sqlx::Error>` and nullable SQL
columns are `Option<T>`.

```rust
mod flash_gen;
use flash_gen::db::Queries;
let pool = sqlx::PgPool::connect(&std::env::var("DATABASE_URL")?).await?;
let queries = Queries::new(pool);
let user = queries.get_user(1).await?;
let users = queries.list_users(20, 0).await?;
```

Set `macros = true` only when a live database is available at compile time;
Flash then emits `sqlx::query!` macros for schema validation.

### Rust validation modes

Rust generation supports two `sqlx` modes. Choose one in `flash.toml`:

```toml
[gen.rust]
enabled = true
out = "src/flash_gen"
driver = "sqlx"
macros = false  # runtime-checked; this is the default
```

With `macros = false`, Flash emits `sqlx::query`, `sqlx::query_as`, and
`sqlx::query_scalar` plus `.bind(...)` calls. Generation and compilation do
not need a live database. SQL syntax, parameter types, and result decoding are
checked when the generated async method executes:

```bash
flash gen
cargo build
DATABASE_URL="postgres://..." cargo run
```

The generated methods still return `Result<T, sqlx::Error>`, so handle runtime
database errors with `?`, `match`, or your application's error type.

Set `macros = true` to emit `sqlx::query!`, `sqlx::query_as!`, and
`sqlx::query_scalar!` instead. These validate SQL against the database at
**compile time**. `DATABASE_URL` must point to a running database whose schema
matches the Flash schema whenever `cargo check` or `cargo build` compiles the
generated code:

```toml
[gen.rust]
enabled = true
out = "src/flash_gen"
driver = "sqlx"
macros = true
```

```bash
flash migrate "sync schema"
flash apply
flash gen -f
DATABASE_URL="postgres://..." cargo check
```

## 16. Filing bugs — `flash issues`

If you hit unexpected behavior or a generation bug:

```bash
flash issues \
  -k bug \
  -t "gen: <short specific summary>" \
  -b "<what you were doing and what happened>" \
  --repro "1. ...  2. ...  3. ..." \
  --expected "<expected>" \
  --actual "<actual, including exact error text>"
```

Flags: `-k` kind (`bug`/`feature`/`question`/`docs`), `--print` preview without
submitting, `-y` skip confirm. Version, OS, and provider are attached
automatically.

## 17. Golden rules for an agent

1. **Read `flash.toml` first** — especially `[gen.*].out` — to know where
   generated files actually live. Never assume `flash_gen/`.
2. **Edit `.sql` files, never generated files.** They are overwritten on `flash gen`.
3. **Re-run `flash gen`** after any schema or query change.
4. **Use `?` placeholders** for this provider (`sqlite`).
5. **Pick the right `:cmd`** — `:one`/`:many` for reads, `:exec`/`:execresult` for writes.
6. **Secrets go in `.env`** via `url_env`; never hard-code connection strings.
7. **Migrations:** `flash migrate "<msg>"` then `flash apply`. Never hand-edit applied migrations.
8. **JSON columns:** use `-- @json` to get typed structs instead of raw strings.
9. **Caching is opt-in:** enable `[cache]`, annotate reads with `-- @cache`, wire `dep`.
10. **Rust macros need a live DB at compile time** when `macros = true`.
11. **Broken generation? Run `flash issues`** with real reproduction steps.
